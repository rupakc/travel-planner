# Source Verification Labels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every Results section tells the traveller how much to trust it — "Verified" (real source or reference data agrees), "Partly verified" (some items confirmed online), "AI-generated — verify before booking", or "Conflicts with reference" — with the concrete checks behind the label, and hotel/activity/place cards show which items were found online.

**Architecture:** A pure backend function `verify_section(name, data, request)` derives a `verification` object from evidence the pipeline already produces — real data sources (Google Flights, Open-Meteo, crawled walking tours), the web searches enrichment already runs (now recorded per item as `link_verified`), and the curated static tables (visa, emergency numbers). The orchestrator attaches it to each section's `data` at every yield (initial, enriched, static), so it streams with the section, is cached with it, and needs no new event type. The frontend renders a chip in each section header with a popover of checks, plus per-item "Found online" badges.

**Tech Stack:** FastAPI orchestrator (SSE), existing enrichment (`backend/app/agents/hotels_agent.py`, `backend/app/services/activity_url_resolver.py`, `backend/app/services/places_url_resolver.py`), static tables (`backend/app/agents/static_results.py`); React 18 + Tailwind; pytest, vitest.

## Design (binding)

Options weighed:
- (a) A second LLM pass that "checks" the first — rejected: an LLM verifying an LLM can hallucinate the verification, adds ~15 calls and latency per search.
- (b) New per-item web searches/fetches for every claim — rejected for v1: competes with enrichment for the DuckDuckGo rate limit, fetching LLM-supplied URLs is an SSRF risk, and adds seconds.
- (c) **Evidence-based labels from data the pipeline already has** — chosen: zero added latency or network calls, deterministic and testable, and honest: when there's no evidence the label says so.

`verification` object (attached as `data["verification"]` on every yielded section dict that has no `error`):
```
{ "level": "verified" | "partial" | "unverified" | "conflict",
  "label": short UI text,
  "summary": one sentence,
  "checks": [ { "label": str, "status": "pass" | "fail" | "info", "detail": str, "url": str | None } ],
  "items_verified": int | None, "items_total": int | None,
  "pending": bool }   # true on the first hotels/activities/places yield while enrichment still runs
```
Labels: verified → "Verified", partial → "Partly verified", unverified → "AI-generated", conflict → "Check details".

Per section (anything not listed → `unverified`, summary "Generated by AI from its training data — verify before booking."):
- **flights:** all results `source` not `estimate` → verified ("Live fares from Google Flights"); mixed → partial; all estimate → unverified ("Estimated fares — prices change; check the airline").
- **hotels:** enrichment sets `hotel["link_verified"] = True` when `_search_url` matched a listing by name, `False` when it searched and found nothing (untouched hotels beyond the enrich cap: key absent). verified if all searched found, partial if some, unverified if none; `items_verified/items_total` over searched hotels; check line "Found online by name: X of N". First (pre-enrich) yield → `pending: true`, level unverified.
- **activities:** resolver marks `link_verified = True` on activities it upgraded to a trusted listing domain (getyourguide/viator/klook/tripadvisor/tiqets/musement); partial if any, else unverified with detail "Links are searches, not specific listings". Prices/ratings always an `info` check "Prices and ratings are AI estimates". Pending on first yield when enrichment will run.
- **places_to_see:** resolver marks `link_verified = True` when it set `info_url` from a search result; same partial/unverified logic.
- **walking_tours:** verified ("Listings crawled from the providers' own pages"), one pass check per `sources[]` entry with status ok (url included); providers that failed → info.
- **weather:** `source == 'open-meteo'` → verified ("Open-Meteo forecast/climate data"); contains `llm-estimate` → partial or unverified accordingly.
- **visa:** static-first. Phase-0 static yield → verified, label "Verified", check "Matches our reference table" + official_url. AI yield: if `get_static_visa(request)` exists — same `visa_type` (normalised: lowercase, hyphen/space-insensitive) → verified; different → **conflict**, summary "AI says <ai type>; our reference table says <table type>. Check the official site.", check status fail with the official_url; never override the AI data. No table entry → unverified ("No reference data for this nationality and destination — confirm on the official site", url = data official_url when present).
- **emergency_card:** compare `emergency_numbers.police/ambulance/fire` with the static table for the destination when present: all equal → verified; any differ → conflict naming the field and both values; no table → unverified.
- **static-backed sim / tips / getting_around / forex Phase-0 yields:** verified label "Reference data" is NOT used — level `verified`, label "Verified", summary "From our curated reference data (may lag recent changes)". Their AI yields → unverified.
- **itinerary, stress_test, packing_list, events, pricing_advisor:** unverified (events add an `info` check per `date_certainty` distribution, e.g. "3 of 5 dates confirmed annual").
- Error results (`{"error": …}`) get no verification (unchanged behaviour; cacheability unaffected — never put a key named `error` in verification).

Orchestrator: one helper `_attach_verification(name, data, request, pending=False)` called right before every section yield listed in `orchestrator.py` (Phase 0 static yields, Phase 1 `ai` yield with `pending=True` for agents that have `enrich`, itinerary, stress_test, packing_list (static and ai), pricing_advisor, enriched re-yield with `pending=False`). Mutating `data` in place is acceptable only if the same dict isn't reused elsewhere; otherwise copy (implementer checks enrich input reuse).

Frontend:
- `frontend/src/components/VerificationBadge.jsx`: chip (emerald Verified / amber Partly verified / gray AI-generated / rose Check details; "Checking…" spinner when pending), button opening an accessible popover (Escape closes, focus returns) listing checks with pass/fail/info icons and links via `safeUrl`.
- `SectionHeader` in `frontend/src/pages/ResultsPage.jsx` renders it for `results[agent]?.verification` (before the status icons). Static → AI transitions just re-render with the new object.
- Per-item "Found online" emerald micro-badge on hotel, activity and place cards when `link_verified === true` (no badge otherwise — absence is not an accusation).
- The section-level conflict also shows as a one-line rose banner inside the Visa / Emergency section body with the official link.
- Chat untouched (knowledge-only; chat emitter doesn't call the helper).

Non-goals: new network checks, LLM verifier, chat, exporting labels, changing which data is shown.

## Global Constraints

- No new dependencies; no new SSE event types; existing event shapes unchanged except the added `data.verification` key.
- Backend: `cd backend && python3 -m pytest -q` (baseline whatever main has at branch time), agents mocked (never call Anthropic/DDG in tests). Frontend: vitest, eslint `--max-warnings 0`, build.
- Labels must never claim verification without evidence; when in doubt, `unverified`.

## Review Focus

1. Visa/emergency conflicts — shown as conflict with both values; AI data not overwritten; no false conflict from formatting differences ("Visa-free" vs "visa free", "112" vs " 112").
2. Hotels beyond the enrichment cap or with empty names — not counted as "not found".
3. Cached search replay — verification present and identical (it's inside data).
4. Static → AI → enriched sequence — chip moves Checking… → final without flicker to a wrong level.
5. Sections with `{error}` or missing lists — no verification, no crash.
