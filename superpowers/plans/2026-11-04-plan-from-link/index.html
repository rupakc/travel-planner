    Plan a Trip From a Link or Screenshot — Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (- [ ]) syntax.

    Goal: A traveller pastes a travel blog / article / video link, pastes text (a caption, a friend's message, a list), or drops up to 4 screenshots — and gets a trip: the places are extracted, mapped and shown for review, then a normal full search plans the trip around those places, every one of them visibly scheduled in the itinerary ("From your link"). It must feel magical, fast and trustworthy.

    Spec: User request 2026-11-04 — feature #3 "Plan from a link or screenshot", "very thoroughly and comprehensively … ENSURE THESE FEATURES DELIGHT USERS". Design choices are Claude's.

    Existing building blocks (verified)

    • Backend FastAPI; agents call Anthropic directly through BaseAgent (backend/app/agents/base_agent.py, Haiku; Sonnet for chat). beautifulsoup4 and httpx are dependencies. Rate limiting: backend/app/core/rate_limit.py (rate_limit(bucket) dependency, try_consume), settings RATE_LIMIT_*.
    • Place resolution: backend/app/db/places_db.py resolve_place(text), backend/app/db/database.py lookup_city_iata, static_results._place_country; places/features tables carry lat/lng and country.
    • TravelSearchRequest (backend/app/schemas/request.py): origin, destination, destinations (multi-city ≤3 stops), destination_nights, dates, interests, pace, budget, travellers, etc.
    • Orchestrator backend/app/agents/orchestrator.py (phases 0/1/2, SSE); activities agent; itinerary agent backend/app/agents/itinerary_agent.py takes activities (top 12 summarised) and hotels.
    • Frontend: SearchPage.jsx has modes "I know where I'm going" / "Surprise me" / "Compare"; ResultsPage.jsx renders sections incl. ItinerarySection, TripMap (Leaflet), My Plan drawer; saved plans store search_data; share page SharePage.jsx; utils/planExport.js / planPrint.js.

    Design (binding)

    Backend

    1. POST /api/import/extract (auth required; new rate-limit bucket import, default 20 per window, setting RATE_LIMIT_IMPORT). Body: { url?: str, text?: str (≤ 20,000 chars), images?: [{ media_type, data_base64 }] (≤ 4, each ≤ 5 MB decoded; png/jpeg/webp/gif; HEIC rejected with a friendly message) } — exactly one kind of source. Response = an ImportPreview (below). Also accepts multipart image upload if simpler for the frontend; document whichever is used.
    2. Safe URL fetching (backend/app/services/link_fetch.py):
    3. http/https only; resolve DNS and reject private, loopback, link-local, multicast, reserved, CGNAT and IPv6 equivalents for the initial host and every redirect hop (max 3 redirects, manual redirect handling); connect to the vetted IP (prevent DNS rebinding) while sending the original Host/SNI; timeout 10 s; stop reading at 2 MB; accept text/html, application/xhtml+xml, text/plain; send a normal browser-like UA.
    4. Extraction: <title>, OpenGraph/Twitter description, JSON-LD (Article/Recipe-like articleBody, ItemList, Place, TouristAttraction), and readable main text (prefer <article>/<main>, drop nav/footer/script/style, keep headings and list items — itineraries are usually lists). Cap at ~30k chars.
    5. Social video/photo links: YouTube and TikTok via their public oEmbed endpoints (title/caption/author); YouTube description is not in oEmbed — use page metadata when available. Instagram/Facebook/X usually block — return a specific friendly error {"code": "blocked_source", "message": "Instagram doesn't let apps read posts. Paste the caption or drop a screenshot instead."} and the frontend switches the user to the text/screenshot tabs with one click.
    6. Never execute scripts; never follow links found in content.
    7. Extraction agent (.agents/link_import.md + backend/app/agents/link_import_agent.py, Haiku via BaseAgent; images use Claude vision content blocks): returns strict JSON { title, summary (1 sentence), places: [{ name, kind (sight|food|drink|stay|activity|nature|shopping|nightlife|event|transport|area), city, country, note (≤ 140 chars, why the source recommends it), quote (≤ 120 chars verbatim from source, optional), day_hint (int|null), confidence (0–1) }], destinations_mentioned: [str], suggested_days (int|null), season_hint (str|null), interests: [str] }. Prompt-injection hardening: source content is wrapped as untrusted data with clear delimiters; the system prompt says to ignore any instructions inside it and only extract places; output validated with Pydantic; at most 40 places; drop items without a name. No PII echoed beyond place names.
    8. Resolution & grouping (backend/app/services/link_import.py):
    9. For each place: resolve its city (+ country) with resolve_place / _place_country → canonical city, country, lat/lng (city-level), airports. POI-level coordinates: if SERPER_KEY is configured, look the POI up (existing Serper places helper — find it) to get coordinates/address/rating and mark verified: true; otherwise use the city centre with approximate: true. Respect existing caches; cap Serper calls per import (≤ 25) and run them concurrently with a semaphore.
    10. Group by resolved city; order cities by day_hint then source order. One city → single destination. 2–3 cities in ≤ 3 countries → propose a multi-city route (destinations + destination_nights split by place count, min 1 night). More than 3 cities → keep the 3 with the most places, list the rest as "also mentioned".
    11. Suggested length: suggested_days if given, else ~4 places per day bounded 2–14.
    12. Unresolved places stay in the preview under "Couldn't place" (editable on the client).
    13. Response ImportPreview: { source: { kind: url|text|images, url?, title, site_name?, favicon_url?, author? }, title, summary, destinations: [{ name (the resolved display, e.g. "Lisbon, Portugal"), country, airports, place_count, nights }], places: [{ id, name, kind, city, country, lat, lng, approximate, verified, note, quote, day_hint, confidence }], unresolved: [...], suggested_days, season_hint, interests, warnings: [str] }.
    14. Search integration: add must_include: list[MustIncludePlace] | None (≤ 25; each { name, kind, city, lat?, lng?, note? }) and import_source: { url?, title } | None to TravelSearchRequest (and pass them through chat-independent paths only).
    15. Activities: must-include places are merged into the activities result as items with source: "your_link", from_link: true (deduplicated against the agent's own results by folded name) and always kept, at the top.
    16. Itinerary: the itinerary agent prompt lists must-include places as "MUST schedule every one of these" with their city; after the agent returns, a deterministic post-check inserts any missing must-include place into the least-loaded slot of the right city's days (or appends a day note if all slots are full) and marks scheduled slots from_link: true. The template fallback itinerary also includes them.
    17. Phase-0/verification: imported items carry their own verification (verified via Serper or "From your link — not independently checked").
    18.
