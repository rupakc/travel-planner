    Drag-and-Drop Itinerary Editing Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: On the Results page itinerary, let users move an activity to another day or time of day (drag-and-drop, plus a keyboard/touch "Move to…" menu), swap two activities, remove one, undo, and reset — with every edit, note, plan pick, export, print view, share page and saved plan following the activity to its new place.

    Architecture: A pure layout overlay selections.itinerary_layout records only where each moved/removed activity now sits, keyed by the activity's original slot key ("<day_number>-<time_of_day>", the de-facto ID the whole app already uses). One pure function, arrangeItinerary(itinerary, layout), turns the original itinerary plus the overlay into the arranged days; every reader renders those arranged days and looks up edits/notes by slot.key (the original key), so nothing is re-keyed on a move. The overlay carries a fingerprint of the itinerary it was made for and is ignored when it doesn't match (stream retry, a saved plan for another trip).

    Tech Stack: React 18, native HTML5 drag-and-drop (no new library — the codebase already uses native DnD), Tailwind 4, vitest + jsdom (createRoot + act).

    Spec: Backlog item #12 in Future_Improvements.md ("Drag-and-Drop Itinerary Editing"). Facts: /private/tmp/claude-501/-Users-rupak-travel-planner/6a423640-de0e-4ae7-a160-af5d4cd4d6e9/scratchpad/research-12.md. All design choices below are Claude's (the user delegated them).

    Design (binding)

    Options weighed: - (a) Overlay of positions keyed by original slot key — chosen. Edits/notes/plan picks/.ics UIDs (slot-${key}) stay attached to the activity with zero re-keying; old saved plans need nothing; one function to test. - (b) Rewrite selections.itinerary and re-key edits/notes/itinerary_slots on every move — rejected: every move mutates four structures, .ics UIDs change (calendar duplicates), and the live Results itinerary is not selections.itinerary. - (c) A DnD library (dnd-kit) — rejected: new dependency; native DnD is the codebase convention and the "Move to…" menu covers touch/keyboard.

    Model: - slotKey(dayNumber, timeOfDay) = \${dayNumber}-${timeOfDay}`. Positions are the three standard timesmorning,afternoon,eveningon each existing day. A slot whosetime_of_dayis not one of the three is displayed where it is and is not movable. -itinerary_layout = { fingerprint: string, positions: { [originalKey]: "-" | null } }—null= removed; a key absent frompositionsstays at its original position.EMPTY_SELECTIONS.itinerary_layout = null. Old plans without it behave exactly as today. -fingerprint= short stable hash of the original itinerary'sday_number|time_of_day|activitylines. A layout whose fingerprint differs from the itinerary being rendered is ignored (rendered as the original) and not written to. - **Move** = put activity A at target position T. If T holds activity B, B moves to A's current position (swap). If T is empty (removed/free), A just moves. Moving to its own position is a no-op. Every day keeps at most one activity per time of day (TimelineView, .ics and print rely on this). - **City rule (multi-city):** a move is allowed only when the source day'scityand the target day'scityare equal (case-insensitive, first comma segment) or either is missing. Swaps must satisfy the rule both ways. - **Remove** = positionnull; the spot shows "Free time" and accepts drops. **Restore** puts a removed activity back at its original position if that is empty, else in the first empty position of its original day, else it stays removed (button disabled with a tooltip). - **Arranged days:** same days, same order and day metadata (date, theme, city); each day's slots = activities now positioned there, sorted morning → afternoon → evening, each slot object is the original slot pluskey(original key) andtime_of_day(its new time).removed: [{ key, slot }]lists removed activities for the UI. - **Costs:** for a day whose contents changed,daily_estimated_cost_usd= sum of its slots' cost (itinerary_edits[key].cost ?? slot.estimated_cost_usd, finite numbers only); untouched days keep the original value.total_estimated_cost_usdis recomputed the same way only when anything changed. Unchanged itinerary → identical numbers to today. - **Plan picks follow:** after every move/remove/restore/undo/reset, eachitinerary_slotsentry is updated to its activity's currentday_number/time_of_day(entries for removed activities are kept, unchanged — the user removes them from the drawer as today). - **Undo:** an in-memory stack of previous layouts (max 20) in ResultsPage; "Undo" reverts the last move/remove/restore. **Reset** clears the layout (with Undo able to bring it back). Both cleared by a new search/remix. - **Where editing happens:** Cards view itinerary only (it is already the edit/notes view). Timeline view, TripMap, drawer, PlanViewModal, SharePage, .ics and print all *display* the arranged itinerary. ChatPage is untouched (chat is knowledge-only; its itinerary is a different shape). - **Health Check:** when the layout has changes, the Trip Health Check section shows one line: "Checked against the original itinerary — your moves aren't re-checked." - **Interaction:** - Each movable slot row has a drag handle (GripVertical,cursor-grab) and isdraggable; drag data uses the custom MIMEapplication/x-itinerary-slot(neverapplication/json, which the drawer treats as a plan). Valid drop targets (other slots and Free-time spots, honouring the city rule) highlight on dragover; invalid ones don't accept the drop. - Each movable slot has a "Move" button opening a small menu listing every valid target as "Day N · Morning" (swaps labelled "Day N · Morning (swap with <activity>)") plus "Remove from day". Fully keyboard operable; Escape closes it; focus returns to the button. - Section toolbar (only when the layout has changes): "N changes" · Undo · Reset. Removed activities listed under "Removed" with Restore. - Status messages in anaria-live="polite"region, e.g. "Moved Sagrada Família to Day 2 · Afternoon". - **Analytics:**track('itinerary_slot_moved', 'results', { method: 'drag'|'menu', swap: bool }),track('itinerary_slot_removed', 'results', {}),track('itinerary_layout_reset', 'results', {})`.

    Non-goals: ChatPage itinerary, re-running the Health Check, adding new activities, more than one activity per time of day, editing in Timeline view, backend changes.

    Global Constraints

    • No new dependencies. No backend changes (selections are stored as opaque JSON).
    • Frontend tests: cd frontend && NODE_OPTIONS=--experimental-require-module npx vitest run; lint npx eslint src/ --max-warnings 0; build npm run build. Pure-logic tests start with // @vitest-environment node; component tests // @vitest-environment jsdom, createRoot + act, mock ../utils/analytics. jsdom has no DataTransfer: tests pass a plain object { setData, getData, types, dropEffect, effectAllowed } on synthetic events.
    • Itineraries with no layout must render, export, print and share byte-for-byte as before (existing planExport/planPrint tests must pass unchanged).
    • Baseline before this work: whatever main has after the best-value package merge (frontend count recorded in the ledger), backend 333.

    Review Focus

    1. Saved plans and share links created before this change (no itinerary_layout) — must look exactly as before.
    2. A layout from another itinerary (fingerprint mismatch) — ignored, never applied to the wrong activities, never crashes.
    3. Edits/notes/plan picks on a moved or swapped activity — follow the activity everywhere (card, drawer, .ics, print, share, saved-plan modal).
    4. Multi-city trips — no cross-city moves through drag or menu, including the swapped partner.
    5. Days whose slots carry odd time_of_day values or fewer than three slots — rendered, the odd ones not movable, free positions droppable.
