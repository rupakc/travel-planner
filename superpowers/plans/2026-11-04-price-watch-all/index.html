    Price Watch for Hotels, Activities and Whole Trips — Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (- [ ]) syntax.

    Goal: Extend the existing fare watch (PR #23) so travellers can also watch (1) a hotel's price, (2) an activity's price, and (3) the price of an entire saved trip (flights + hotel + activities + other costs), with the same delightful, never-spammy alerts (bell, Alerts page, toasts, browser notifications, optional email).

    Spec: User requests 2026-11-04: "similar to the Watch this fare alert for flights create the same alerts for 1. Hotel Prices 2. Prices of the Activities 3. Price of the entire saved trip (all moving parts)"; activity prices: "Rely on AI estimates and also scrape the web to get the latest data (GetYourGuide, Viator)"; "VERY VERY THOROUGHLY AND RIGOUROUSLY … NO REGRESSIONS … MASSIVELY PARALLEL AGENTIC EXECUTION".

    Verified facts (controller, 2026-11-04)

    • Only flight prices are live today (serp_flights, SerpAPI google_flights). Hotel and activity prices are AI estimates from hotels_agent / activities_agent.
    • Hotels — live source works: SerpAPI engine=google_hotels (q="hotels in Lisbon", check_in_date, check_out_date, adults, currency=USD, hl=en, gl=us) returned 20 properties with rate_per_night.extracted_lowest, total_rate.extracted_lowest and a property_token per property (e.g. "Lumen Hotel & The Lisbon Light Show" $100/night, $398 total for 4 nights). A property can be re-checked by property_token (SerpAPI google_hotels property-details mode).
    • Activities: getyourguide.com and viator.com return HTTP 403 to automated clients even for robots.txt — direct scraping would require defeating bot protection and is out of scope (will not be built). Legitimate observed-price source that works: SerpAPI engine=google search (e.g. "Belem Tower tour Lisbon getyourguide"): GetYourGuide organic results carry rich_snippet.top.detected_extensions.price (+ currency, rating, reviews) and extensions: ["Starting from $11.63"]. Viator results in the sample had no price snippet (use when present). backend/app/services/activity_url_resolver.py already queries SerpAPI engine=google — reuse its client/caching patterns.
    • Existing fare watch (merged): backend/app/services/fare_watch.py (pure evaluate, check_watch, scheduler run_due/run_scheduler/start_scheduler, per-signal references + re-arming, cooldown, step()), backend/app/db/fare_watch_db.py (tables fare_watches, fare_watch_history, fare_watch_quota, fare_watch_user_quota; leasing claim_watch, reserve_calls), backend/app/db/notifications_db.py, routes backend/app/api/routes/fare_watches.py + notifications routes, email services/alert_email.py; frontend components/alerts/* (WatchDialog, WatchCard, WatchFareButton, Sparkline, NotificationBell, AlertToast, alertKinds.js), pages/AlertsPage.jsx, context/AlertsContext.jsx, services/api.js.

    Design (binding)

    Price sources (honesty rules)

    • Observed prices: flights (google_flights), hotels (google_hotels by property_token), activities (Google search snippet price of the matched GetYourGuide/Viator listing). Every observed price carries source (e.g. google_hotels, getyourguide_via_google), observed_at, and a link.
    • Estimated prices: AI estimates from the original search (activities/hotels without a live match, and "other" trip costs such as SIM, local transport). Estimates are frozen at watch creation (not re-asked), always labelled "estimate" in UI/email, and never trigger alerts on their own. A watch whose every component is an estimate cannot be created (friendly message: "We can't find a live price for this yet").
    • Never present an estimate as a live price; never invent drops.

    Data model (additive; flight tables untouched)

    • New table price_watches: id, user_id, kind (hotel | activity | trip), plan_id (nullable), title, subtitle, subject JSON (kind-specific: hotel {name, city, property_token, check_in, check_out, adults, rooms}; activity {name, city, listing_url, listing_title, provider, query, travellers}; trip {plan_id, components: [...]}), currency, alert_mode (any_drop | below_target), target_price, email_enabled, status (active|paused|expired|error), baseline_price, last_price, lowest_price, last_notified_price, last_notified_at, own_peak_price (re-arm), failure_count, last_error, check_count, last_checked_at, next_check_at, lease_until, expires_on (date: check-in / activity date / trip departure), created_at, updated_at.
    • New table price_watch_history: watch_id, checked_at, price, breakdown JSON (trip), observed JSON. ≤ 120 rows/watch.
    • Reuse notifications (new kinds: hotel_drop, hotel_target, activity_drop, activity_target, trip_drop, trip_target, watch_expired, watch_error with data.watch_kind), the SerpAPI daily budget + per-user share (reserve_calls, same quota tables, same FARE_WATCH_* settings — one shared budget), and the scheduler loop (one loop processes due fare watches and due price watches).

    Rules (shared engine)

    • Extract the own-dates signal logic of fare_watch.evaluate (reference = last alerted price or baseline, step() = max($15, 5 %), re-arm on rebound ≥ step with peak reference, target re-arm at target + step, 24 h cooldown cap with further-drop override, never on baseline, never on rises, baseline-already-good rule) into a pure, kind-agnostic module backend/app/services/price_rules.py used by BOTH fare watches and price watches. Fare-watch behaviour must not change: every existing fare-watch test (incl. test_fare_watch_sequences.py) stays green unmodified; add an equivalence test that runs the old sequences through both paths.
    • Trip-specific: alert threshold on the total = max($25, 4 %); the notification explains the change by component ("Your Lisbon trip is $112 cheaper: flights −$70, hotel −$42"). Components that are estimates are held fixed. A trip watch also raises a component-level heads-up only through the total (no separate per-component alerts from a trip watch).

    Checking

    • Hotel check: 1 SerpAPI call (google_hotels property by property_token for the watch's dates/adults) → total stay price (all nights, all rooms) + nightly; property unavailable for the dates → unavailable observation (not a failure; UI "Sold out for your dates"; no alert; counts toward expiry/error only after 3 consecutive).
    • Activity check: 1 SerpAPI google call with the stored query → find the stored listing_url (normalised: scheme/host/path, ignore query) among results → snippet price × travellers (price is "from" per person: label "from $X per person"); listing not found → fall back to same-provider best name match (name_match) only if similarity high; else unavailable (no alert).
    • Trip check: re-price live components (flight via the existing fare path for the plan's selected flight/dates; hotel via property; up to 5 observed activities, rotating if more), estimates fixed; total = Σ; ≤ 8 calls per check, reserved all-or-nothing against the budget; cached results reused free.
    • Cadence 12 h ± jitter (same as fares); expiry the day of expires_on.

    Creating watches (API, auth, ownership 404s, light_ai rate bucket for create/check-now, 503 without SerpAPI, 409 at the active limit — FARE_WATCH_MAX_ACTIVE_PER_USER counts fare + price watches together)

    • POST /api/price-watches {kind:"hotel", hotel:{name, city, check_in, check_out, adults, rooms?}, alert_mode, target_price?, email_enabled?} → match the AI hotel to a live property via google_hotels (q="<name> <city>", dates, adults; pick by name_match ≥ threshold) → store property_token, take baseline. No confident match → 422 {code:"no_live_price", message:"We couldn't find live prices for this hotel on Google Hotels.", suggestions:[up to 3 live properties with similar names/area and their prices]}; the UI offers to watch a suggestion instead.
    • {kind:"activity", activity:{name, city, date?, travellers}} → search GYG/Viator listing ("<name> <city> getyourguide", then viator) → best name match with a price snippet → baseline; none → 422 no_live_price with the AI estimate shown and up to 3 priced listings found as suggestions.
    • {kind:"trip", plan_id} → build components from the saved plan's selections (selected flight → flight component via existing fare code; selected hotel → hotel match as above; selected activities → activity matches; everything else in the cost breakdown (SIM, transport, tips…) → estimate components); report which components are live vs estimate in the response; baseline total.
    • GET /api/price-watches (with history + breakdown), GET/PATCH/DELETE /api/price-watches/{id}, POST /api/price-watches/{id}/check, POST /api/price-watches/match (is this hotel/activity/plan already watched? no live calls).

    Frontend (delight bar)

    • Watch buttons: hotel cards (Results + Chat), activity cards (Results + Chat), My Plan selected hotel/activities, and "Watch whole trip" on saved-plan cards, PlanViewModal and the My Plan drawer (when the plan is saved). Watched state "Watching · $398".
    • Create dialog (shared shell with the fare dialog, kind-specific body): hotel shows the matched Google Hotels property name (so the user sees what is tracked), nightly + total, dates; activity shows the matched listing (provider logo-free text, title, rating, "from $X per person", link); trip shows the breakdown table (component, price, Live/Estimate badge) and the total. Modes: any drop / below target. Email toggle. "Not this one?" for hotel/activity → pick a suggestion.
    • Alerts page: tabs/filter chips All · Flights · Hotels · Activities · Trips (counts), a card per kind via a kind→card registry (components/alerts/cards/), trip card with stacked breakdown bar (flights/stay/activities/other), Live/Estimate badges, sparkline of the total, "what changed" line; actions as for fares (Check now, Pause, Edit, Delete, Re-plan, Book/Open listing).
    • Notifications/toasts/emails per kind with natural copy ("🏨 Lumen Hotel dropped to $352 for 10–14 Dec (−$46)", "🎟️ Belém walking tour is now from $9.90 (−$1.73)", "🧳 Your Lisbon trip is $112 cheaper: flights −$70, hotel −$42").
    • Quality: responsive 360 px, keyboard, ARIA live, reduced motion, no layout shift, polling only while visible (existing).

    Global Constraints

    No new dependencies. No network in tests (record sanitized SerpAPI fixtures — strip api_key — under backend/tests/fixtures/serpapi/). Fare-watch behaviour unchanged (all existing tests green, untouched). No scraping of sites that block automated access. Backend pytest + ruff; frontend vitest + eslint + build; mkdocs --strict. Live SerpAPI usage during development ≤ 15 calls per agent.

    Execution (parallel)

    • Phase 1 (parallel, separate worktrees):
    • P1-core (pw/core): price_rules.py extraction (+ equivalence tests), price_watches + history tables, generic check pipeline with a PriceSource protocol async def check(watch: dict, api_key: str) -> PriceObservation and a kind→source registry, scheduler extension, API skeleton (/api/price-watches CRUD/check/match with kind dispatch to registered sources), notification kinds, frontend: Alerts page tabs + kind→card registry + generic dialog shell + api.js functions. Ships with a fake test source for tests only.
    • P1-hotel-src (pw/hotel-src): backend/app/services/hotel_prices.py — pure adapter: find_properties(name, city, check_in, check_out, adults, api_key) -> list[HotelOffer], match_property(name, offers) -> HotelOffer|None, price_property(token, check_in, check_out, adults, api_key) -> HotelPrice|None; parsing robust to missing fields; fixtures recorded live (≤ 6 calls).
    • P1-activity-src (pw/activity-src): backend/app/services/activity_prices.py — find_listings(name, city, api_key) -> list[ActivityListing] (GYG then Viator queries), match_listing(name, listings), price_listing(listing, api_key) -> ActivityPrice|None (re-search, URL-normalised match, snippet price parse incl. "Starting from $X", currencies), fixtures recorded live (≤ 6 calls).
    • Phase 2 (parallel, after Phase 1 merges into feat/price-watch-all): P2-hotel (hotel source registration + hotel UI), P2-activity (activity source + UI), P2-trip (trip aggregator + trip UI + Watch whole trip).
    • Phase 3: parallel reviews (one per Phase-2 branch + one regression reviewer on fare watch), fixes, controller live E2E, merge.
