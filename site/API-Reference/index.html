    API Reference

    The backend is a FastAPI app (backend/app/main.py). Every endpoint is under /api except /health and /health/agents. A running instance serves Swagger UI at /docs, ReDoc at /redoc and the schema at /openapi.json; locally that is http://localhost:8001/docs.

    Authentication. Send the token from POST /api/auth/login as Authorization: Bearer <token>. Tokens are HS256 JWTs valid for 24 hours. In the tables below:

    • user: a valid token for an active user is required (401 otherwise).
    • admin: the user must also be an admin (403 otherwise).
    • optional: anonymous calls are allowed. With a valid token for an active user, the Taste Graph is applied and rate limits count per user; otherwise (including a deactivated user's token) the caller is anonymous and counted per IP.
    • none: no token needed.

    Rate limits

    Endpoints that call the AI agents are rate-limited per caller (the signed-in user, or the client IP for anonymous requests) over a sliding 10-minute window (backend/app/core/rate_limit.py). Every accepted request counts, including cached responses and requests later rejected as invalid (422) or unauthenticated (401); only requests answered with 429 do not.

    Bucket Endpoints Default limit
    search POST /api/search, POST /api/search/sync 10
    chat POST /api/chat 30
    compare POST /api/compare/destination 30
    discover POST /api/discover 10
    import POST /api/import/extract, POST /api/import/resolve-place 20
    light_ai POST /api/flights, /hotels, /activities and their /filtered variants, /flights/fare-calendar, /visa, /sim, /tips, /getting-around, /forex, /itinerary, /events, /walking-tours, /layover, /stress-test, /nearby, /live-check, /fare-watches (create), /fare-watches/{id}/check, /price-watches (create), /price-watches/{id}/check, PUT /auth/email 60

    Each bucket is counted separately, with one exception: a chat turn that starts a full trip plan (including a refinement that rebuilds the itinerary) also takes one token from the caller's search bucket, so searches and chat-planned trips share one budget; over it, the already-open chat stream answers with a friendly delta saying roughly how many minutes to wait, then done (no 429, no error). Over the limit the API answers 429 Too Many Requests with a Retry-After header (seconds) and:

    {"detail": "Too many requests — please wait 42 seconds and try again."}

    Limits are configurable (see Configuration). The counter is in-process, so each backend process counts on its own.

    Auth

    Accounts, sessions, OAuth sign-in, the account area, avatars, export and deletion, the daily AI quota, the game and admin invites are specified in Accounts API, the frozen contract the web, iOS and Android clients build against. This page covers the original auth endpoints; the legacy request and response keys are unchanged.

    POST /api/auth/login

    { "username": "admin", "password": "your-password" }

    Response (401 for wrong credentials or an inactive account):

    {
  "access_token": "eyJ...",
  "token_type": "bearer",
  "user": { "username": "admin", "is_admin": true, "requires_password_change": false, "email": null }
}

    If requires_password_change is true, the frontend sends the user to /change-password first.

    POST /api/auth/change-password

    { "current_password": "old", "new_password": "at-least-8-chars" }

    Returns {"access_token": "...", "token_type": "bearer"} with a fresh token. 400 if the current password is wrong or the new one is shorter than 8 characters.

    GET /api/auth/me

    Returns { "username", "is_admin", "requires_password_change", "email" }.

    PUT /api/auth/email

    {"email": "me@example.com"} sets the account email (trimmed, lower-cased; not verified, so the route is rate-limited in the light_ai bucket); "" clears it and turns email off on all the user's fare watches. Returns {"email": ...}. 422 for an address that isn't local@domain.tld; 409 when another account uses it. Set from the Preferences page.

    Self-registration is POST /api/auth/signup (see Accounts API). Admins can also create users:

    POST /api/admin/users

    { "username": "newuser", "password": "TemporaryPassword123", "email": null, "is_admin": false }

    201 with the user (no password hash). The new user must change the password on first login. 409 for a duplicate username or email, 400 for a password under 8 characters. POST /api/admin/users/{username}/reset-password takes {"new_password": "..."}.

    Search

    POST /api/search

    The main endpoint. It streams results as Server-Sent Events. Auth: optional. Responses for a complete, error-free run are cached for 30 minutes and replayed instantly.

    Request body (TravelSearchRequest, backend/app/schemas/request.py):

    {
  "origin": "London",
  "destination": "Tokyo",
  "departure_date": "2026-06-01",
  "return_date": "2026-06-14",
  "nationality": "British",
  "interests": ["food", "history", "nature"],
  "budget_usd": 4000,
  "num_travelers": 2,
  "adults": 2, "children": 0, "seniors": 0, "infants": 0,
  "accessibility_needs": [],
  "residence_permits": [],
  "existing_visas": [],
  "destinations": null,
  "destination_nights": null,
  "pace": "balanced",
  "serendipity": 0.5,
  "locale": "de"
}

    locale is optional: one of en, es, de, fr, hi, zh, bn (anything else is a 422). When it is not English, every model call for the request is told to write its human-readable text in that language (JSON keys, enum values, codes, URLs, prices, currency codes, dates and place names stay as in English), and the response cache keeps a separate entry per language. Absent or en behaves exactly as before. The static Phase 0 data (visa, SIM, tips, getting around, forex, emergency card) stays English until the AI result replaces it. The same field is accepted by POST /api/chat, /api/discover, /api/compare/destination and the single-agent and /filtered routes. The web app sends the UI language.

    Two optional fields carry a trip imported with POST /api/import/extract:

    • must_include (at most 25): places the plan must contain, each {name, kind, city, town?, lat?, lng?, note?, quote?, verified}. city is the trip stop the place belongs to, and town is its own town when that differs (a day trip). They lead the activities results as source: "your_link", from_link: true items, folding in the agent's own copy of the same place, and they stay even when the activities agent fails. Each item's verification_note is "Located on Google Maps" or "From your link — not independently checked". After the itinerary (AI or template) is built, a deterministic check marks the slots that name each place (from_link, link_place, link_places, link_quote, link_note). A slot counts only if the place's name appears in its activity or location text as one contiguous, ordered phrase. The match ignores accents and filler words ("the", "de"), treats hyphens, spaces and apostrophes alike, and drops a possessive "'s". Run-together spellings count only on whole tokens ("Senso-ji" ~ "Sensoji", "Time Out" ~ "TimeOut"). So "Tokyo Tower" is not "Tokyo Skytree … tallest tower", and "Ark Hills" is not "Park Hills". On multi-city trips, the slot must also be on a day in the place's own city. Travel slots may name a place through their activity text ("Train to Sintra for Pena Palace", "Hop on Tram 28"), but are never replaced. Arrival, departure and hotel slots never stand for a place. Missing places go into the most replaceable slot on a day in the right city: free time first, food at lunch or dinner, and never a logistics slot on any day. Logistics means arrivals, departures, check-in/out, flights, trains, Shinkansen, buses, ferries, drives, transfers, "→", "to ", two of the trip's stops joined by "–", "⇒" or "to", or a transport category. Each stop's travel-in day is skipped when that city has another day. A place of kind transport is never put into a slot: unmatched, it becomes a note on one of its city's days. A replaced slot drops the old activity's cost, booking link and times, and that cost is taken off the day's and the trip's totals. When every such slot already holds a link place, the place goes into the day's link_extras. The itinerary also carries link_coverage: {total, scheduled, extras, missing}.
    • import_source: {url?, title}, where the trip came from. url must be http(s). Saved plans keep it in search_data, and the share page, print view and calendar export show "Inspired by …".

    destinations and destination_nights describe a multi-city trip (see Multi-City Trips). taste_context is set by the server from the user's Taste Graph; a client value is ignored. origin and destination may be city names, typeahead labels or airport codes; the validator resolves them to airport codes for live flight search (see Place and Airport Data).

    Response: Content-Type: text/event-stream. Each event is data: {JSON}\n\n, and : keepalive comments are sent while agents run.

    Event Phase source Notes
    visa, sim, tips, getting_around, forex 0, then 1 static, then ai Static-backed; an AI error is not sent, so the static data stays
    confidence 0 static Travel Ease grade: total out of 100 and green/amber/red, from visa ease, safety, English friendliness, cost vs budget and tourist infrastructure
    emergency_card 0, then 1 static, then ai Static-backed
    agent_status — — {agent, status: "searching" \| "done"} for the 15 agents at start, and for stress_test
    flights, weather, hotels, activities, places_to_see, walking_tours, events 1 ai hotels, activities and places_to_see are sent twice: before and after link enrichment
    packing_list deferred ai (static for the template fallback) Starts when activities and weather are in
    pricing_advisor deferred ai Starts when flights have at least 3 results; skipped on error or after 120 s
    itinerary 2 none Starts when activities and hotels are in; template fallback after 60 s
    stress_test after the itinerary ai 90 s timeout; on error an error section is sent
    done — — Always last

    Every non-error section carries data.verification (see Agent System). An agent that fails sends {"error": "..."} as its data (except the static-backed ones), so the UI can show "not available" instead of waiting. When the monthly AI spend cap has tripped, the data is {"error": "AI limit reached for this month — try again on the 1st.", "error_code": "ai_limit"}; single-agent routes return the same object.

    POST /api/search/sync

    Same request and agents, run sequentially; returns a single JSON object. For testing only.

    {
  "destinations": [
    {
      "city": "Lisbon",
      "country": "Portugal",
      "estimated_cost_usd_low": 1400,
      "estimated_cost_usd_high": 2200,
      "visa_type": "visa-free",
      "visa_verified": true,

    POST /api/import/extract

    Plan from a link: reads a web page, pasted text or screenshots and returns the places in it, resolved and grouped into a trip for the traveller to review. Auth: user. Bucket: import.

    Request body: exactly one of:

    {"url": "https://blog.example/48-hours-in-lisbon"}
{"text": "48 hours in Lisbon: Time Out Market, Belém Tower, LX Factory…"}
{"images": [{"media_type": "image/png", "data_base64": "iVBORw0…"}]}

    text is at most 20,000 characters. images holds 1–4 PNG, JPEG, WebP or GIF images of up to 5 MB each, decoded. On Gemini (Vertex AI reads no GIF) a GIF is converted to PNG when Pillow is installed, otherwise refused with gif_unsupported. The type is sniffed from the bytes, and HEIC is refused with a friendly message. Images are sent as JSON base64, not multipart.

    Link fetching (backend/app/services/link_fetch.py): - Only http and https on the default ports, with no credentials in the URL. - The host is resolved, and every address must be public. Private, loopback, link-local, multicast, reserved and CGNAT ranges are refused, as are their IPv6, IPv4-mapped, NAT64, 6to4 and Teredo forms. The connection goes to that vetted IP, with the original Host header and TLS SNI, so DNS rebinding cannot redirect it. - Redirects are followed by hand, at most 3, and each hop is checked again. - There is a 10-second ceiling, and only HTML, XHTML and plain text are accepted. - Only gzip and deflate compression is requested and accepted. The body is read as raw bytes, at most 2 MB, and inflated with a bounded zlib decompressor that stops at 2 MB of output, so a compression bomb cannot grow. Brotli, zstd, stacked and unknown encodings get unsupported_encoding. - Every hop sends Connection: close, so no pooled connection is reused across hosts. - HTML is parsed with BeautifulSoup in a worker thread, off the event loop. - From the page come the title, the OpenGraph and Twitter description, JSON-LD (articleBody, ItemList, places and attractions) and the readable main text, capped at 30k characters. The main text comes from the biggest article or content block, keeps headings and list items, and drops nav, footer, script and style. - YouTube and TikTok links are read through their public oEmbed endpoints, plus the YouTube watch page's description. - Instagram, Facebook, X and Threads get a specific blocked_source error, including when a shortener redirects to them. - Scripts are never run, and links in the content are never followed.

    Extraction: the link_import agent (.agents/link_import.md, the agent model; screenshots go as vision image blocks). Everything taken from the source (site name, title, author, description, text) is wrapped as untrusted data between <<<SOURCE_<nonce>>>> and <<<END_SOURCE_<nonce>>>> markers. The nonce is random for each request, and anything in the source that looks like a marker is stripped. Only fixed labels ("a web page", "pasted text", "screenshots") sit outside the fence. The system prompt says to ignore any instructions inside the source. The output is validated with Pydantic: places without a name are dropped, at most 40 are kept, fields are clamped, and a quote is kept only when it appears in the source text word for word: case-sensitive, whole words only, with curly and straight quote marks treated as the same. A day_hint is kept only when the source text itself names that day ("Day 2", "Day 2–3", "days 4 to 5").

    Resolution (backend/app/services/link_import.py): - Each place's city is resolved with resolve_place to a canonical town, country, coordinates and airports. A town within 45 km of a bigger stop in the same country joins that stop as a day trip. - Stops are ordered by the source's day hints, then by source order. With more than 3 stops, the 3 with the most places are kept and the rest are listed in also_mentioned. - Nights are split by place count, with at least 1 per stop. The trip length is suggested_days, or else about 4 sightseeing places a day, between 3 and 14 days. - With SERPER_KEY, up to 25 places are looked up on Google Maps (5 at a time, cached). A hit within 60 km of the town that shares a word with the name gives exact coordinates (verified); otherwise the place sits at its town centre (approximate).

    Response (200) — ImportPreview:

    {
  "source": {"kind": "url", "url": "https://…", "title": "…", "site_name": "Wander Blog", "favicon_url": "https://…", "author": null},
  "title": "48 hours in Lisbon",
  "summary": "Viewpoints, pastries and a day trip to Sintra.",

  "places": [{"id": "p1", "name": "Time Out Market", "kind": "food", "city": "Lisbon", "country": "Portugal", "destination": "Lisbon, Portugal", "lat": 38.707, "lng": -9.146, "approximate": false, "verified": true, "address": "…", "rating": 4.4, "note": "Lunch under one roof", "quote": "start at Time Out Market", "day_hint": 1, "confidence": 0.95}],

 "date": "2026-12-10", "travellers": 2, "listing_url": null, "estimate_price": 30}}

    name and city are required; date (optional, must be in the future) ends the watch, which otherwise runs 180 days; travellers is 1–20 (default 1); estimate_price is the AI's per-person estimate, shown labelled in a no_live_price answer and never watched. The server searches Google (SerpAPI) for " getyourguide" (then Viator) and watches the best-matching specific listing; category or attraction pages are never watched. The price is the listing's per-person "from" price × travellers (last_observation.unit_price is per person), as Google results show it — getyourguide.com and viator.com are never fetched. A no_live_price answer suggests up to 3 priced specific listings; their spec carries listing_url, and a watch of a picked listing is its own subject (the original activity stays unwatched). A check that can't find the listing, finds it without a price, or finds it in another currency is unavailable (observed.reason: not_found, no_price, currency_changed). A listing matches only when it names every place / proper-noun word of the activity; generic tour words ("small group walking tour") never carry a match alone. Activity alerts use a step of max(1, 5 %) in the listing's currency. "Already watching" is by name, city and travellers (the date only ends the watch), and also by the same listing and travellers however it was found.

    GET /api/price-watches, GET /api/price-watches/{id}

    The caller's price watches (?kind=hotel|activity|trip to filter; ordered by expires_on) or one, each with its history.

    POST /api/price-watches/match

    Body: {"kind": ..., "<kind>": spec, "plan_id": ...} as for create. Returns {"watch": {...}} or {"watch": null} (also for an unknown kind or an unusable spec); makes no live lookup.

    PATCH /api/price-watches/{id}

    Any of status ("paused" / "active"), alert_mode, target_price, email_enabled. Resuming an error watch clears both streaks and checks it on the next tick ("Retry"). 409 to resume an expired watch or past the active limit; 422 as for fare watches.

    DELETE /api/price-watches/{id}

    Deletes the watch and its history. Returns {"deleted": true}.

    POST /api/price-watches/{id}/check

    "Check now" (also on a paused watch). Like the fare-watch check, it never answers from the 30-minute cache: the look is live, refreshes the cache, and its calls count against the daily budget and the caller's share. Returns the watch plus check_status (checked, unavailable, failed, errored, postponed, expired, skipped, deleted) and notification. 429 / 409 / 503 as for fare watches. Rate-limited (light_ai).

    As the fare-watch unsubscribe link, for one price watch (its own signed token; a fare-watch token is refused with 400).

    /api/alerts/*

    Price alerts 2.0. The full contract (objects, advice codes, error codes, delivery rules) is the frozen Alerts API. In short: every route needs a signed-in user and acts only on the caller's watches (404 watch_not_found). GET /api/config reports features.alerts_api: 2, features.price_alerts_v2 (PRICE_ALERTS_V2_ENABLED) and features.live_prices (a SerpAPI key is set). The read routes always exist; the pipeline behind them (drop facts, savings rows, Deal-hunter XP, delivery rules, digest) runs only when PRICE_ALERTS_V2_ENABLED=true. Every watch object also carries pending_first_check, and drop notifications may carry extra data.drop / data.game keys, and a price_digest kind with data.digest exists; clients that don't know them ignore them.

    Mobile app: push devices and Near me

    Added for the Android app. Every route needs a signed-in user and only touches that user's data. An FCM token only ever travels in a request body, never in a URL, so request and access logs never carry one; logs show at most its last 6 characters.

    POST /api/devices

    Registers the app's FCM registration token for push alerts.

    {"token": "eXaMpLe...:APA91b...", "platform": "android", "locale": "de-DE"}

    token 1–4096 characters; platform only "android" (the default); locale optional (≤ 35). → 200 with the device, token masked to its last 6 characters:

    {"id": 12, "token": "…Xy12Ab", "platform": "android", "locale": "de-DE",
 "created_at": "2026-11-05T09:00:00.123456+00:00", "last_seen_at": "2026-11-05T09:00:00.123456+00:00"}

    Registering again refreshes locale and last_seen_at (call it on every app start and token refresh). A token registered by another user moves to the caller (a shared phone). A user keeps at most 20 devices; the least recently seen is dropped.

    GET /api/devices

    {"items": [device, ...]}, most recently seen first, tokens masked as above.

    DELETE /api/devices/{id}

    Removes one of the caller's devices by its id (for example a lost phone, from a "Your devices" list). 204; 404 {"detail": "Device not found"} when the caller has no device with that id (another user's device is never touched); 422 for a non-numeric id.

    POST /api/devices/unregister

    Sign-out: {"token": "<the full FCM token>"} → 204, always (idempotent; a token the caller doesn't own is left alone and gets the same answer). Call it before dropping the JWT.

    Push messages

    When FCM_SERVICE_ACCOUNT_FILE is set (/health push_configured), every new fare- or price-watch notification is also pushed to each of the owner's devices over FCM HTTP v1, in the background as a data-only message (no notification block, so the app always builds the notification itself): Android priority high (normal for watch_expired / watch_error), and string data (the notification's title and body ride in data too):

    {"kind": "fare_drop", "notification_id": "42", "link": "/alerts?watch=7", "watch_id": "7"}

    link is the web deep link (data.links.alerts of the notification: /alerts?watch=<id> for fare watches, /alerts?kind=<kind>&watch=<id> for price watches); price watches add watch_kind. The notification itself is unchanged in /api/notifications. A deactivated user gets no pushes. A token is deleted only when FCM says it is dead (error code UNREGISTERED, or INVALID_ARGUMENT naming message.token); every other failure, including a bare 404 from a wrong Firebase project, keeps the token, is logged, and the notification stays in-app only.

    POST /api/nearby

    Bucket: light_ai.

    {"lat": 35.0116, "lng": 135.7681, "interests": ["temples", "food"], "limit": 8}

    lat −90…90, lng −180…180, interests optional (≤ 20, each trimmed and 1–60 characters; default: the saved preferences' interests), limit 1–20 (default 8). The nearest place in the local GeoNames table (towns of 1,000+ people) within 75 km is chosen; a ward or suburb yields to a place at least 10× bigger within 15 km ("Kamigyō-ku" → Kyoto). The existing activities agent then runs for "Place, Region, Country" ("Portland, Maine, United States"; the region is left out when it repeats the name, "Kyoto, Japan") with those interests and the caller's Taste Graph. → 200:

    {
  "place": {"name": "Kyoto", "region": "Kyoto", "country": "Japan", "country_code": "JP",
            "lat": 35.02107, "lng": 135.75385, "distance_km": 1.4},
  "items": [{"name": "Fushimi Inari Taisha Early Morning Hike", "category": "culture",
             "similarity_score": 0.95, "rating": 4.8, "review_count": 12000,
             "source": "getyourguide", "booking_url": "https://www.getyourguide.com/s/?q=...", "...": "..."}]
}

    items are the activities agent's results, unchanged (the shape of POST /api/activities), first limit. region is the state / province (GeoNames first-level division) name, or null. distance_km is from the point to the place's centre. Results are cached for an hour per 0.05° cell (about 5 km), place, interests and taste profile. Errors: 404 {"detail": {"code": "no_place", "message": "..."}} when no known place is within 75 km; 502 {"detail": {"code": "agent_error", "message": "..."}} when the agent fails (not cached); 503 with code: ai_limit when the monthly AI spend cap has tripped.

    Near me v2: sections: true

    {"lat": 38.72, "lng": -9.14, "limit": 6, "sections": true, "language": "en"}

    Same place lookup as above, then one Gemini call grounded with Google Maps around lat/lng (language: optional BCP-47-style code such as en or pt-PT, default en; limit: per section, 1–10, default 6; interests as above, used as a hint). Without sections (or with false) the route is exactly v1, so installed apps keep working. → 200:

    {
  "place": {"name": "Lisbon", "region": null, "country": "Portugal", "country_code": "PT",
            "lat": 38.72, "lng": -9.14, "distance_km": 0.4},
  "sections": [
    {"id": "see",  "title": "Places to see",  "items": []},
    {"id": "eat",  "title": "Places to eat",  "items": [
      {"name": "Time Out Market Lisboa", "summary": "One-line why, from the grounded answer",
       "maps_uri": "https://maps.google.com/?cid=…", "place_id": "ChIJ…", "category": "eat"}]},
    {"id": "shop", "title": "Places to shop", "items": []},
    {"id": "stay", "title": "Places to stay", "items": []}
  ],
  "attribution": "Google Maps",
  "sources": [{"title": "Time Out Market Lisboa", "uri": "https://maps.google.com/?cid=…"}]
}

    The four sections always come in this order and may be empty. The model answers under one heading per group (## See, ## Eat, ## Shop, ## Stay) with one place per line (Name - why; split on the first dash, or on : only when there is none). A heading is a # line, a fully bold line or a bare section word; its section comes from a keyword anywhere in it (see/sight, eat/food/restaurant/drink, shop/market, stay/hotel/sleep — so ## Where to eat, ### 🍽️ Eat, ## 1. See work), and a heading naming no section, or several, stops the current one so its items are dropped rather than misfiled. Each line is matched to a Maps grounding chunk whose title matches the place's name (folded exact, or one containing the other for names of 6+ characters; chunks the line's grounding supports cite are tried first, but never taken on a support alone), and the item takes the chunk's title (without Google's " - Google Maps" suffix), uri (maps_uri) and placeId (place_id, without the places/ prefix; may be null). A place without a Maps chunk with a link is dropped, so no item is invented. sources lists every Maps chunk with a link. Each model call has a 45 s request timeout and a 50 s ceiling including the wait for the shared AI concurrency gate, with no SDK-level retries; an answer with text but no Maps chunks is retried once, then returned with empty sections. A Review of … chunk (a link to a review of the place) loses that prefix, the place's own chunk is preferred over it, and a place appears at most once. Location privacy: v2 passes the request's lat/lng to Google Maps grounding through Vertex AI (Google's retrieval config) so results are near the user; clients round them to about 100 m first. The backend never stores or logs the coordinates (request logs hold the path only, and the llm_usage line holds counts). Not cached (Google's Maps grounding terms; see Live web check and Near me). Errors: 404 no_place and 502 agent_error (the model call failed) as in v1; 422 for limit > 10 with sections: true; 503 {"detail": {"code": "ai_limit" | "ai_billing" | "grounding_unavailable", "message": "…"}} — grounding_unavailable ("Live web and map results need the Gemini provider.") when the backend runs on the Anthropic provider (v1 is unaffected).

    Live web check

    POST /api/live-check

    Bucket: light_ai. Signed-in users only. "Search the web now" for one of the caller's watches: a Gemini call grounded with Google Search, built server-side from the stored watch (route, dates and travellers; hotel, dates and guests; activity, city and date; a trip's flight, hotel and activities). There is no free-text prompt: unknown fields are 422.

    {"kind": "hotel", "watch_id": 123}

    kind is flight (a fare watch, /api/fare-watches/{id}) or hotel / activity / trip (a price watch of that kind, /api/price-watches/{id}). → 200:

    {
  "kind": "hotel",
  "watch_id": 123,
  "checked_at": "2026-11-06T18:00:00Z",
  "summary": "Plain-text answer from Gemini (grounded), unmodified.",
  "quotes": [{"label": "Booking.com, 3 nights", "amount": 412.0, "currency": "EUR", "source_index": 0}],
  "sources": [{"title": "booking.com", "uri": "https://vertexaisearch.cloud.google.com/grounding-api-redirect/…"}],
  "searched_for": ["memmo alfama lisbon price 1-4 dec 2026"],
  "disclaimer": "From a live web search just now. Prices change quickly — check the provider before booking. Not used for your price alerts."
}

    summary is the model's grounded text (whitespace-trimmed only). sources are the web grounding chunks with a link, once per link, as Google returns them. quotes are parsed from the answer's bullet lines (- Seller, what: EUR 412; also - **Seller:** EUR 412 and Seller:EUR 412 — the label is everything before the last colon ahead of the price). Each keeps only an amount and ISO 4217 currency copied from the text, and an unclear price gives no quote rather than a wrong one. The text is tokenised into whole numeric runs: a run counts only if it is one number in comma-thousands / dot-decimal form (1 234, 1'234, 1.234,56, 412,50 are rejected whole, never read as part of the run); no letter may touch it (5k) and no magnitude word may follow (1.5 million, 2 lakh); the currency must touch it, with at most one space, on one side only — a known ISO code (EUR 412, 412.50 EUR; TAP, NYC aren't currencies) or an unambiguous symbol (€, £, ₹, US$, C$, A$, NZ$, S$, HK$; never a bare $ or ¥); a code touching two numbers (99 EUR 2 nights) voids the line. The price must be covered by a grounding support whose chunk is one of sources (source_index): by the support's byte range when Vertex gives one (a missing start means 0), else by its text (at least 12 characters, containing the price). Anything else is left out, so quotes may be empty. searched_for are the web searches the model ran (show them as "Searched for", linking to Google Search). Nothing is written to the database, cached or used for alerts; only an llm_usage line (tokens, search-query and chunk counts, latency; never content) is logged.

    Each model call has a 45 s request timeout and a 50 s ceiling including the wait for the shared AI concurrency gate, with no SDK-level retries; an answer without web sources is retried once. Errors: 404 {"detail": "Watch not found"} (not the caller's watch, or not of that kind); 409 {"detail": {"code": "watch_expired", "message": "This trip's date has passed, so there's nothing left to check."}} when the watch is expired or its date (departure; check-in / activity date / trip departure via expires_on) is more than a day in the past in UTC (before yesterday, so a date that is still today somewhere on Earth can be checked), without a model call; 429 rate limit; 502 {"detail": {"code": "live_check_failed", "message": "…"}} when the model fails or the answer still has no grounding sources; 503 {"detail": {"code": "ai_limit" | "ai_billing" | "grounding_unavailable", "message": "…"}}.
